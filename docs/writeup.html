The machine behind the code

Tour (Pulse with PygmyProjects / VirtualDreams, third at Assembly 1998) is the elder sibling of 73 million seconds. It is a Watcom C/C++ 32-bit program running flat under a DOS extender (PMODE/W 1.33), drawing 640x480 in 8, 16 and 32 bits per pixel into a VESA linear framebuffer, with sound from the IMS library playing FastTracker modules. The target was a Pentium MMX (1997, P55C: two in-order pipes, U and V, with a 3-cycle FPU and a 1 MMX multiplier) and in 1998 a Pentium II (an out-of-order P6 core, where the old pairing games matter less and partial registers hurt). The compiler output is ordinary - sar/shl/sbb division idioms, stack frames, fnstsw/sahf compares - and the demo's own inner loops are hand-written assembly sitting in the middle of it, in the effect library (0x14xxxx-0x17xxxx), in "object 2" (0x1b000, NASM-style kernels) and in the bzip-style decoder.

Rules of the Pentium game used below, in one paragraph: simple integer instructions (mov, add, sub, and, cmp, lea, inc/dec) can issue two per clock, one in each pipe (pairing), unless the second depends on the first; shifts and adc/sbb pair only in the U pipe; a register used as an address in the cycle after it was written costs a clock (AGI stall); a taken branch pairs in V; fxch is free next to an FP op; the FPU has a 3-cycle latency but starts a new operation every cycle, and fdiv runs alongside integer code; MMX multiplies have one unit with latency 3; the data cache does not allocate on a write miss. Cycle remarks in the text are estimates from these rules, not measurements.

1. Clearing memory with a hand-made prefetch

0x103ad0 / 0x103b07 - Watcom runtime memset

The C library's fill routine is the first thing every effect calls (it clears 640x480x32 buffers, 1.2 MB, many times a second). It is not the naive rep stosd: it aligns the destination, then writes 32 bytes per turn with eight plain mov [eax+n],edx and, before the stores of each line, issues a dummy read of the next 32-byte line, cmp byte ptr [eax+0x20],dl.

Why: the Pentium and Pentium MMX data cache does not allocate a line on a write miss (the P6 family, i.e. Pentium II, does). A long run of stores into cold memory therefore produces a stream of individual bus writes. A read of one byte of the next line makes the cache fetch the whole line while the CPU is busy storing the current one; when the next turn arrives its stores hit the cache and are written back as a burst. The cmp pairs for free (U/V), it modifies only flags, and there is no software-prefetch instruction before the Pentium III's prefetcht0.

2. Truncating floats with the FPU control word

0x103d1a - helper used by fade, xfade, table builders

C semantics for (int)x is truncation toward zero, but the x87 rounds to nearest by default (fistp turns 2.7 into 3 and 2.5 into 2). Watcom's usual answer is a slow __CHP helper. Pulse wrote a 10-instruction helper that switches the rounding control field of the FPU control word to "chop", runs frndint, and restores the old word. The caller then does an ordinary fistp, which is now exact because the value is already an integer.

The constant is subtle: the code reads the current control word with fnstcw, stores a copy 4 bytes up the stack, and overwrites byte 1 of the working copy with 0x1f. With the default 0x037f that gives 0x1f7f: bits 10-11 (RC) = 11b = truncate, bits 8-9 (PC) = 11b = 64-bit mantissa (unchanged), bit 12 set (infinity control, irrelevant). Writing a whole byte instead of masking bits saves two instructions and a register.

103d1a  push eax                          ; st(0) = x on entry; push eax just to reserve 4 bytes
103d1b  wait                              
103d1c  fnstcw word ptr [esp]             ; current control word -> [esp]
103d1f  wait                              
103d20  push dword ptr [esp]              ; second copy (the one to restore) ends up at [esp+4]
103d23  mov byte ptr [esp + 1], 0x1f      ; byte 1 of the working copy := 0x1f  -> 0x1f7f = round toward zero
103d28  fldcw word ptr [esp]              ; load the chop word
103d2b  frndint                           ; now truncates
103d2d  fldcw word ptr [esp + 4]          ; restore the original word
103d31  wait                              
103d32  lea esp, [esp + 8]                ; lea (not add) frees the two words without touching flags
103d36  ret

A use: building a 512-entry byte table (lowpass init, 0x1117d9)

1117d9  fld qword ptr [0x1ad396]          
1117df  fild dword ptr [esp + 0x14]       
1117e3  fadd st(1)                        
1117e5  mov ebx, dword ptr [esp + 0x14]   
1117e9  fmul st(2)                        
1117eb  lea ecx, [ebx + 1]

1117f3  fistp dword ptr [esp + 4]         ; fistp is exact now
1117f7  mov al, byte ptr [esp + 4]        ; low byte of the result
1117fb  mov dword ptr [esp + 0x14], ecx   
1117ff  mov byte ptr [ebx + 0x1ffbc8], al

Cost: fldcw is a slow, partly serialising instruction (several to ten-plus cycles each on a Pentium, worse on the P6), so the helper is for per-frame values and table setup, never for per-pixel work; the per-pixel conversions use the "magic number" trick in the next section. Checked on the original: trunc(2.7)=2, trunc(-2.7)=-2, trunc(-0.9)=0, while the same sequence without the helper gives 3, -3 and 2.5->2, 3.5->4 (banker's rounding).

const trunc = (x) => Math.trunc(x);     // or x | 0 when |x| < 2**31

3. Float to 16.16 in three instructions, and an FDIV hidden behind integer code

0x16b4e5 and 0x16b972 - the scanline setup of the polygon fillers

The triangle fillers need edge positions and texture coordinates as 16.16 integers. A fistp would give a plain integer, and scaling by 65536 first costs a multiply. The classic "magic number" does it with one add: the float stored at 0x1c2488 is 0x51c00000 = 1.5 x 236. Adding it to x forces the result into the binade [236, 237) where one unit in the last place of a double is 2-16; the 52-bit mantissa then holds round(x*65536) in its low bits. Store the sum as a qword and read the low dword: that is x in 16.16 (signed, ties to even). No fistp, no control-word games, and the add pairs with the surrounding FPU work.

16b972  fld st(3)                         ; copy of the value to convert (an edge x, or u / v)
16b974  fadd dword ptr [0x1c2488]         ; fadd the magic constant (float32 1.5*2^36)
16b97a  mov eax, dword ptr [0x1c2498]     ; integer work proceeds while the FPU adds
16b97f  mov ebx, dword ptr [0x1c245c]     
16b985  cmp eax, dword ptr [0x1c24a8]     
16b98b  jae 0x16ba98                      
16b991  fstp qword ptr [0x1c2454]         ; store as a DOUBLE ...
16b997  mov edx, dword ptr [0x1c2454]     ; ... and read its low dword: that is x*65536, rounded
16b99d  add ebx, 0xfff0                   ; ebx = left edge in 16.16 (stored the same way earlier)
16b9a3  shr ebx, 0x10                     ; (x + 0xfff0) >> 16: ceil with a 1/4096 pixel of slack = the fill rule
16b9a6  add edx, 0xffe0                   ; right edge uses 0xffe0
16b9ac  shr edx, 0x10

Checked against the original (harness): 304 random floats in +-30000, including tiny ones, give exactly round-to-nearest-even(fround(x)*65536) every time (max error 0).

The FDIV that costs nothing

On the Pentium an fdiv takes 39 cycles at the default 64-bit precision but, unlike other FPU instructions, only the FPU is busy: integer instructions keep issuing. The setup code starts the slope division and then spends 25 instructions on integer work (splitting two 16.16 deltas into a fractional high half and an integer low half, and writing them into the inner loop's immediates) before the result is first used by fmul st(1),st(0) at 0x16b572. The divide is completely hidden.

16b4e5  fdiv dword ptr [0x1c2448]         ; fdiv: starts now, finishes ~39 cycles later, FPU busy but the integer pipes are free
16b4eb  mov eax, dword ptr [0x1c2454]     ; low dword of the magic-number double stored earlier = du in 16.16
16b4f0  mov ebx, dword ptr [0x1c245c]     
16b4f6  mov ecx, dword ptr [0x1c2454]     
16b4fc  shl eax, 0x10                     ; shl 16: the FRACTIONAL part as a 32-bit addend (for add esi,imm)
16b4ff  mov edx, ebx                      
16b501  shr ecx, 0x10                     ; shr 16: the INTEGER part (for adc cl,imm)
16b504  mov dword ptr [0x16bab5], eax     ; patch: inner loop immediate (see the self-modifying section)
16b509  shl ebx, 0x10                     
16b50c  mov byte ptr [0x16bae0], cl       ; patch: another immediate
16b512  shr edx, 0x10                     
16b515  mov dword ptr [0x16bae3], ebx     
16b51b  mov byte ptr [0x16bae9], dl       
const MAGIC = 1.5 * 2 ** 36;                         // the float32 0x51c00000 stored at 0x1c2488
const f64 = new Float64Array(1), lo32 = new Int32Array(f64.buffer);
function toFixed16(x) {                              // float -> 16.16, round to nearest even
  f64[0] = Math.fround(x) + MAGIC;                   // fld / fadd dword [0x1c2488] / fstp qword
  return lo32[0];                                    // mov edx,[low dword]   (little endian)
}

4. Four floats at a time: a hand-scheduled FPU pipeline

0x1521bd - volume vector library (mulvolume, addvolume, fadevolume ...)

The voxel effects work on 16x16x16 fields of float32 (4096 values, 16 KB). Add, subtract, multiply and scale are one tiny hand-written routine each, and all of them are software-pipelined for the Pentium's x87: fmul has a 3-cycle latency but can start every cycle, fld and fxch are nearly free, and fxch may pair with the preceding FP instruction in the V pipe at no cost. So instead of "load, multiply, store" per element, the loop keeps four multiplies in flight: loads and multiplies of elements 0..3 interleave, fxch st(2) brings a finished product to the top just in time for fstp, and the stores are issued in the order that matches the stack (4, 0, 12, 8) rather than memory order. The loop control (dec ecx / jne) and the three pointer increments run in the shadow of the last stores.

1521bd  shr ecx, 2                        ; ecx = float count; shr 2 = groups of 4 (16 bytes)
1521c0  fld dword ptr [edx]               ; a0 on the stack
1521c2  fmul dword ptr [ebx]              ; a0*b0 starts (memory operand: no separate load)
1521c4  fld dword ptr [edx + 4]           ; a1 loads while a0*b0 is still in the multiplier
1521c7  fmul dword ptr [ebx + 4]          
1521ca  fld dword ptr [edx + 8]           
1521cd  fmul dword ptr [ebx + 8]          
1521d0  fxch st(2)                        ; fxch pairs with the previous FP op: free reordering of the stack
1521d2  fld dword ptr [edx + 0xc]         
1521d5  fmul dword ptr [ebx + 0xc]        
1521d8  fxch st(2)                        
1521da  fstp dword ptr [eax + 4]          ; results leave in stack order: elements 1, 0, 3, 2
1521dd  fstp dword ptr [eax]              
1521df  fstp dword ptr [eax + 0xc]        
1521e2  fstp dword ptr [eax + 8]          
1521e5  add eax, 0x10                     ; integer bookkeeping overlaps the fstp latency
1521e8  add edx, 0x10                     
1521eb  add ebx, 0x10                     
1521ee  dec ecx                           
1521ef  jne 0x1521c0                      ; dec/jne: the branch pairs with the dec
1521f1  ret

Verified in the harness: 4096 random float pairs through 0x1521bd (multiply) and 0x1521f2 (add) are bit-identical to the float32 operations. Every FPU result is rounded to float32 by fstp dword; an exact extended product of two float32 values rounds the same way as a float32 multiply, so JavaScript's Float32Array reproduces it exactly.

// 4 floats per iteration like the asm; every store rounds to float32, as fstp dword does.
function mulVec(dst, a, b, n) {              // dst, a, b: Float32Array, n multiple of 4
  for (let i = 0; i < n; i += 4) {
    dst[i]     = a[i]     * b[i];     dst[i + 1] = a[i + 1] * b[i + 1];
    dst[i + 2] = a[i + 2] * b[i + 2]; dst[i + 3] = a[i + 3] * b[i + 3];
  }
}

5. MMX saturating arithmetic and the negative-index loop

0x1e7a8..0x1e829 - object 2 blend kernels

Object 2, a block of NASM-style code the program carries separately, holds the blend loops for 8-bit-per-channel buffers: add, add-and-double, subtract. One paddusb clamps eight bytes at once, replacing what on a plain Pentium takes a compare, a branch or a lookup table per byte (the next two sections show how the same saturation was done without MMX).

The loop shape is the one to steal: it counts up to zero with a negative index. The prologue negates the length and biases all three pointers by it (sub esi,ecx subtracts a negative number: esi moves to the end). The loop body then addresses [esi+ecx] and increments ecx by 8; when it reaches 0 the flags from add ecx,8 are already right for jne. No separate counter, no cmp: four instructions of overhead become two, and they pair (add in U, jne in V).

1e7a8  neg ecx                           ; ecx = -length
1e7aa  sub esi, ecx                      ; esi, ebx, edi all += length: they now point at the END of their arrays
1e7ac  sub ebx, ecx                      
1e7ae  sub edi, ecx                      
1e7b0  movq mm0, qword ptr [esi + ecx]   ; movq: 8 bytes of source A
1e7b4  paddusb mm0, qword ptr [ebx + ecx]; paddusb with memory operand: 8 saturating byte adds (the load and the add do not pair: dependent)
1e7b8  movq qword ptr [edi + ecx], mm0   ; 8 bytes out
1e7bc  add ecx, 8                        ; ecx += 8 sets ZF when it reaches 0
1e7c2  jne 0x1e7b0                       ; so no cmp: jne uses the flags of the add
1e7c4  emms                              ; emms: hand the FPU back (MMX aliases the x87 registers)
1e7c6  ret

Harness check: 4096 random bytes through each entry equal numpy's clamped results for add (0x1e7a8), add then double (0x1e7c7) and subtract (0x1e7e9). The fourth entry, 0x1e808, is a bug that shipped: it does psubusb mm0,[ebx+ecx] and then psubusb mm0,mm0, i.e. x-x = 0, so that blend mode writes zeros (mode 33 in the "blend" effect) - confirmed by the harness.

const addus8 = (dst, a, b, n) => { for (let i = 0; i < n; i++) dst[i] = a[i] + b[i]; };
// dst is a Uint8ClampedArray: the store itself saturates, exactly paddusb.  psubusb = same with a[i]-b[i].

6. A two-pass IIR blur on four columns at once

0x1f83c - "lowpass" effect, 8-bit 320x200 buffers

The lowpass effect smooths an 8-bit image vertically with an exponential filter y += (x-y)*t/128, first top-to-bottom into a scratch column, then bottom-to-top back into the image (which cancels the phase lag). An IIR filter is a serial dependency chain, so it cannot be vectorised along the filter direction. The trick is to vectorise across it: one movd loads four horizontally adjacent pixels, punpcklbw against a zero register widens them to four 16-bit lanes, and the four filters run in parallel with psubw / pmullw / psraw 7 / paddw. Each iteration is a 12-instruction loop for 4 pixels.

Two more details. The weight t is replicated into the four lanes once (mov ah,al / shl / or then punpcklbw). And the loop counter is folded into the address register: ebp starts at 0xffff0600 and grows by the row stride 0x140 until it wraps to exactly zero after 200 rows, so add ebp,0x140 ... jne needs no cmp. MMX instructions leave the flags alone, so the jne may sit two MMX instructions after the add that feeds it. The pmullw (3-cycle latency, one multiplier) makes the recurrence the critical path; the loads, the pack and the pointer updates are all scheduled in its shadow.

1f83c  pushal                            ; (pushal) al = t (0..128) on entry
1f83d  mov ah, al                        ; replicate t into all 4 bytes ...
1f83f  mov ebx, eax                      
1f841  shl ebx, 0x10                     
1f844  or eax, ebx                       
1f846  mov dword ptr [0x1e934], eax      
1f84b  mov ebp, 0xffff0600               
1f850  push esi                          
1f851  push edi                          
1f852  pxor mm7, mm7                     ; mm7 = 0, mm6 = t in four 16-bit lanes
1f855  movd mm6, dword ptr [0x1e934]     
1f85c  punpcklbw mm6, mm7                
1f85f  sub esi, ebp                      ; esi -= ebp (= -0xfa00): esi = column start + 64000, ebp counts rows from -200*320
1f861  mov edi, 0x1ee3c                  ; edi = scratch column buffer (200 dwords)
1f866  sub edi, 4                        
1f86c  movd mm1, dword ptr [esi + ebp]   
1f870  movd mm0, dword ptr [esi + ebp]   ; mm0 = the next 4 source pixels (mm1 still holds the previous output)
1f874  punpcklbw mm1, mm7                
1f877  punpcklbw mm0, mm7                
1f87a  psubw mm0, mm1                    ; mm0 = x - y  (signed 16-bit lanes)
1f87d  pmullw mm0, mm6                   ; * t
1f880  psraw mm0, 7                      ; >> 7 (arithmetic)
1f884  paddw mm1, mm0                    ; y += ...
1f887  add edi, 4                        
1f88d  add ebp, 0x140                    ; ebp += 320: next row AND loop counter
1f893  packuswb mm1, mm7                 ; pack back to bytes (saturating)
1f896  movd dword ptr [edi], mm1         ; store 4 filtered pixels in the scratch column
1f899  jne 0x1f870                       ; ZF from the add ebp,0x140 two instructions up: wraps to 0 after 200 rows

Harness check: for t = 0,1,17,64,100,128, a random 320x200 image and a 4-column strip, the output of the original equals the JavaScript below byte for byte, and the other columns are untouched.

// Forward then backward recursive filter down 4 adjacent columns of a 320x200 8-bit image.
function lowpass4(src, dst, col, t) {                // 0 <= t <= 128 (weight in 1/128)
  const acc = [0, 0, 0, 0], tmp = new Uint8Array(200 * 4);
  for (let c = 0; c < 4; c++) acc[c] = src[col + c];          // first pixel primes mm1
  for (let y = 0; y < 200; y++) for (let c = 0; c < 4; c++) {
    acc[c] += ((src[y * 320 + col + c] - acc[c]) * t) >> 7;   // psubw, pmullw, psraw 7, paddw
    tmp[y * 4 + c] = acc[c];                                  // packuswb + movd [edi]
  }
  for (let y = 199; y >= 0; y--) for (let c = 0; c < 4; c++) {
    acc[c] += ((tmp[y * 4 + c] - acc[c]) * t) >> 7;           // second pass, bottom to top
    dst[y * 320 + col + c] = acc[c];
  }
}

7. Saturating add of four bytes without MMX

0x152e5a - additive filler for 32-bit buffers

The fillers also exist in a flavour that runs on a plain Pentium. To add a 32-bit texel to a 32-bit pixel with per-channel saturation it uses a SWAR sequence (SIMD within a register) of seven ALU instructions. Both operands have bit 0 of every byte cleared (the destination is masked on the fly with and ebx,0xfefefefe, the texels are stored that way). Adding them can then never carry out of bit 0, so bit 0 of the sum's byte k+1 is exactly "byte k overflowed". and edx,0x01010100 collects those three flags; edx - (edx>>8) turns each flag 0x100 into 0xff in the byte below; or forces those bytes to 255. The price is one bit of precision (7-bit effective channels) and an unsaturated top byte, which the 32-bit buffers do not use.

152e5a  mov ebx, dword ptr [edi]          ; ebx = destination pixel
152e5c  mov al, byte ptr [ecx + 0x1869f]  ; al = texture index byte at [ecx + base] (ecx = packed v:u, base patched)

8. RGB565 saturation with an XOR carry detector and a 4-entry table

RGB565 has fields of 5, 6 and 5 bits with no spare bits, so the 32-bit trick does not apply. The 16-bit filler recovers the carries instead: after add bx,ax the expression dest ^ texel ^ sum has bit k set exactly when a carry entered bit k. Masking with 0x820 (bit 5 = first green bit, bit 11 = first red bit) tells whether blue and green overflowed; the carry out of bit 15 is still in CF, and sbb eax,eax turns it into a full mask for red. The two flag bits, shifted down by 5, form an index into a four-entry table of 16-bit masks placed at 0x1ba99c: [0]=0, [1]=0x001f, [0x40]=0x07e0, [0x41]=0x07ff, sparse because the index is built from bits 0 and 6. A mov from [edx*2+table] replaces what would be two compare-and-branch pairs.

It is not a perfect saturating add: the overflowing carry has already incremented the next field by 1 before it is forced to its maximum. Measured against an exact per-channel min(sum, max) it differs in 47% of uniformly random pairs (red and green are +1 too large in about 24% each, blue never), and never by more than one step - invisible in a 5/6-bit image, and the port reproduces it.

9. Self-modifying scanline filler: immediates as registers

The texture coordinates are a fixed-point DDA with the carry flag as the fixed-point carry: u lives as 8 integer bits in cl and 16 fractional bits in the top half of esi; v is the same in ch and ebx. add esi,fracstep produces the carry, adc cl,intstep consumes it. Because ecx's low 16 bits are v:u, they are directly the index into a 256x256 texture: no shifts or masks per pixel. The add esi is issued early in the loop and the matching adc cl eight instructions later, with MMX instructions in between that do not touch the flags (the MMX unit is a separate pipeline from the flag logic), so the carry survives.

Per pixel the loop does a premultiplied alpha blend, dst = dst*(63-a)/64 + texel, in MMX: punpcklbw widens the four channels, pmullw multiplies by (63-a), psraw 6 divides, packuswb narrows and paddb adds the texel. The destination is addressed with a negative count in edx ([edi+edx*4], edx runs up to 0), the same trick as before. 10. A reaction-diffusion step as one table lookup, with stochastic rounding

0x20400 patcher and 0x2073e kernel - cellrd (Gray-Scott)

The Gray-Scott chemistry of the "cellrd" effect would be a few floating point multiplies per cell. The original precomputes the whole update as two tables: the new value of a cell is a function of its own state and the sum of its neighbours, packed by the caller into one index (sum<<10 | B<<5 | A, tables of 776K and 280K 16-bit entries). The kernel is then one lookup per cell that yields an 8.8 fixed-point value. Truncating 8.8 to the 5-bit state would freeze slow reactions, so the high byte of table + noise is taken, where the noise byte is a running sum of a 32 KB random table, walked with a stride that shrinks from 0x41 to 1: stochastic rounding (dithering) with a long-period, cheap noise source.

The three tables (T1, T2, noise) are not kept in registers: an entry routine at 0x20400 copies their addresses into the 12 displacement fields of the kernel (mov [0x20762],ecx ..., one store per site, run once per effect instance), and the kernel is unrolled 4x so that each mov ax,[eax+eax+imm32] already has its table address. [eax+eax+T] is the way to say "T + 2*eax" with a 16-bit table: the x86 has the scale factors 1/2/4/8 but only on the index register, and two base registers can be added instead (the encoding is a SIB byte with eax as base and index). The loop counter doubles as the noise stride: add ebp,[esp] / dec dword [esp].

// Reaction kernel of cellrd: one table lookup per cell, 8.8 result, stochastic rounding by a noise walk.
function cellRow(out1, out2, s1, s2, T1, T2, N, st) {          // 260 cells, two output fields
  let step = 0x41;
  for (let it = 0, j = 0; it < 0x41; it++, step--) {
    for (let k = 0; k < 4; k++, j++) {
      st.ebx = (st.ebx & ~255) | ((st.ebx + N[st.ebp]) & 255);  // add bl,[ebp+N]
      out1[j] = ((T1[s1[j]] + st.ebx) >> 8) & 255;              // mov ax,[eax+eax+T1]; add eax,ebx; ah
      out2[j] = ((T2[s2[j]] + st.ebx) >> 8) & 255;
      st.ebp = (st.ebp + step) & 0x7fff;                        // add ebp,[esp] ; and ebp,0x7fff
    }
  }
}

14. The dlz bit reader: DEC does not touch the carry

function decodeDlz(src) {
  let p = 0x11, w = src[p] | src[p + 1] << 8, n = 16; p += 2;
  let out = new Uint8Array(1 << 16), o = 0;
  const put = (v) => { if (o === out.length) { const t = new Uint8Array(o * 2); t.set(out); out = t; } out[o++] = v; };
  const gb = () => { const b = w & 1; w >>= 1; if (--n === 0) { n = 16; w = src[p] | src[p + 1] << 8; p += 2; } return b; };
  const copy = (bh, bl, len) => { const off = ((bh << 8) | bl) - 0x10000; for (let i = 0; i < len; i++) put(out[o + off]); };
  for (;;) {
    if (gb()) { put(src[p++]); continue; }
    const b2 = gb(), bl = src[p++]; let bh = 0xff;
    if (!b2) {
      if (gb()) { for (let i = 0; i < 3; i++) bh = ((bh << 1) | gb()) & 255; bh = (bh - 1) & 255; copy(bh, bl, 2); continue; }
      if (bl !== 0xff) { copy(bh, bl, 2); continue; }
      if (gb()) continue;
      return out.slice(0, o);
    }
    bh = ((bh << 1) | gb()) & 255;
    if (!gb()) {
      let dh = 2;
      for (let i = 0; i < 3; i++) { if (gb()) break; bh = ((bh << 1) | gb()) & 255; dh = (dh << 1) & 255; }
      bh = (bh - dh) & 255;
    }
    let cl = 3;
    for (; cl <= 6; cl++) if (gb()) break;
    if (cl > 6) {
      if (gb()) cl = gb() ? 8 : 7;
      else if (gb()) cl = src[p++] + 0x11;
      else { let c = 0; for (let i = 0; i < 3; i++) c = (c << 1) | gb(); cl = c + 9; }
    }
    copy(bh, bl, cl);
  }
}

15. A bzip-style decoder: branch-free Huffman walk and self-patched tables

0x173b25..0x173bd8 - TOUR3.XM (2.9 MB -> 2.1 MB)

The soundtrack module is the one file packed with the block-sorting coder ("BlockSort" in the error strings): Huffman, move-to-front, run-length codes and an inverse Burrows-Wheeler transform. The decoder is hand-written assembly (interleaved with deliberate nops: the mark of someone scheduling for the U and V pipes), and it has three good ideas.

Bit buffer. The bits are kept left-aligned in edx. When fewer than 8 remain, one unaligned mov edi,[esi] reads four bytes, bswap makes them big-endian, and edi,0xffffff00 keeps three, shr edi,cl slides them under the bits already present and or merges them: 24 fresh bits for 8 instructions, no per-bit loop. Fast Huffman. The top 8 bits of edx index a 256-entry table of node pointers; a node holds symbol and code length, so most symbols cost one lookup. For longer codes the symbol field is -1 and the walk continues bit by bit without a branch: add edx,edx shifts the next bit into CF, sbb ebp,ebp turns it into 0 or -1 and mov edi,[edi+ebp*4+4] selects child 0 or child 1.

Self-patching. The count table and the inverse-BWT vector are addressed through 0x3e7 placeholders ([ecx*4+0x3e7], [edi*4+0x3e7]): the entry routine 0x173aa7 patches the real addresses into seven sites (0x173bac, 0x173bb3, 0x173bbb, 0x173c07, 0x173c0f, 0x173c1d, 0x173c7e), which frees registers for the bit buffer. The move-to-front step shifts the list with a short byte loop (mov ch,[eax+list-1] / mov [eax+list],ch / sub eax,1 / jns).

// canonical-Huffman symbol read: 8-bit fast table, then a branch-free tree walk
function readSym(br, fast) {             // br.peek(n) / br.skip(n): MSB-first bit reader
  let node = fast[br.peek(8)];
  if (node.sym >= 0) { br.skip(node.len); return node.sym; }
  br.skip(8);
  do { const bit = br.peek(1); br.skip(1); node = node.child[bit]; } while (node.sym < 0);
  return node.sym;                       // asm: child index = -CF via sbb, so no branch on the data bit
}
function mtf(list, i) { const b = list[i]; list.copyWithin(1, 0, i); list[0] = b; return b; }

How the loader and the packers work

TOUR.EXE is two packers deep. The 16-bit MZ stub (file offset 0x40, entry 0x5e) is an LZEXE-style decompressor (the get-bit subroutine of section 14): it unpacks the PMODE/W 1.33 extender in place, relocates it and jumps to it. PMODE/W then reads the overlay appended to the EXE (signature PMW1 at file offset 0x2d00), decompresses the program's objects with its own LZ, applies the relocations, switches the CPU to 32-bit protected mode with its own DPMI-like host and jumps to the Watcom start-up code. The result is an LE-like image: object 1 (code, data and bss, loaded at linear 0x100000, about 1.6 MB with bss) and object 2, 40 KB at 0x1b000 holding the MMX kernels and the cell-automaton kernel. All objects are read/write/execute, which is why the filler templates and the kernels can patch themselves.

To extract the program we did not reimplement either decompressor: re/unpack_pmodew.py runs the original stub in Unicorn in real mode, emulates the DOS calls it makes (open/read/seek of TOUR.EXE itself, memory queries), follows the switch to protected mode, and lets PMODE/W unpack everything; the loaded memory is then cut into re/image.bin and re/obj2.bin. After that, every later check in this page uses the harness: a snapshot of the booted program (re/state.bin) from which single functions are called with the Watcom register convention (args in EAX, EDX, EBX, ECX), their output compared with the port. The data archive TOUR.98 has its own coders: 58 records of "dlz" (section 14), one byte-RLE, one adaptive-Huffman LZ (type 3, for RYMDLEGO.XM) and the BWT coder of section 15 for the 2.9 MB module; JPEG and PNG are stored as they are. The 640x480x32 screen is the VESA linear framebuffer itself: the demo writes straight into the card's memory.
