What you are watching

Tour by Pulse (together with Pygmy Projects and Virtual Dreams / FLT) was shown as entry #16 of the PC demo competition at Assembly 1998 in Helsinki, where it finished 3rd with 752 points. It is a ~4½-minute real-time demo: a software 3D engine, volumetric effects (metaballs, marching cubes), feedback effects, a reaction–diffusion simulation and a procession of photographs, all running at 640×480 in true colour on a Pentium-class PC under MS-DOS, synchronised with a tracker module.

The NFO explains a design choice: the music player has SB32 disabled: the music is over a megabyte in size, it's got to be mixed ‘by hand’; there is no kind of ‘download time’ whatsoever.

This site runs a JavaScript re-implementation of that engine. The original script and assets are read as they are; every effect was re-written from the disassembly of the original code and checked against the original executable running inside a CPU emulator. Nothing is pre-rendered.

The retro context

1998: DOS is not dead yet

Windows 98 had just shipped, but the demoscene still wrote for MS-DOS: the program owns the machine, switches the graphics card to a mode of its choice and talks to the hardware directly. TOUR.EXE is a 32-bit protected-mode DOS program: a DOS extender (here Daredevil & Tran's PMODE/W 1.33, the free alternative to Rational's DOS/4GW) switches the CPU to protected mode and gives the Watcom C++ code a flat address space, while DOS is still there for files and keyboard.

640×480 in true colour — through VESA

The classic VGA mode 13h (320×200, 256 colours) is gone: Tour asks the video card, through the VESA BIOS extension, for a 640×480 linear frame buffer in 16 or 32 bits per pixel (the demo even prints Select 640x480 video mode and try running UNIVBE when the card has no VESA BIOS; PTC, thanked in the NFO, is a pixel-surface library from that era). Effects render into off-screen buffers of 8, 16 or 32 bits per pixel; 8-bit buffers carry intensity for feedback effects and are turned into colour by a palette stage.

Small downloads

The archive is packed with a handful of home-made coders (an LZ with a flag-bit stream, a block coder for the module) because 1998 demo parties had a size limit and no-one wanted a long loading time.

How the engine works

The architecture is data-driven. A 4 KB text script, script.unr, creates named buffers and then adds events: an event is an instance of an effect type with input buffers, output buffers and a parameter string. Every frame the engine runs all events in creation order. Effects chain like a patch-bay: a 3D scene renders over a picture blitted into SCREEN, a doubleimage doubles a 320×240 buffer to 640×480, a blend adds a layer… Script lines carry a time stamp that is not seconds but a pattern order / row of the tracker module, so the visuals stay glued to the music whatever the speed of the machine.

createBuffer SCREEN 640 480 32
createBuffer TEMP8 320 240 8
createBuffer LORES 320 240 32
...
addEvent echo5 eko5 {TEMP8} {TEMP8} {0.5*Frame}
addEvent palette pa {TEMP8} {LORES} {medusa.pal}
addEvent doubleimage di {LORES} {SCREEN} {}
addEvent blend blendpa {SCREEN EFXLAYER} {SCREEN} {1}
9 0 deleteEvent filow            ; at order 9, row 0 of the module

Parameters may be expressions compiled by a small evaluator and evaluated each frame with the variable Frame = time since the event started, in hundredths of a second.

Reverse-engineering the executable

  1. Unpacking, twice. TOUR.EXE is a tiny MZ stub whose 16-bit code decompresses (an LZEXE-style bit reader) the PMODE/W extender; PMODE/W then reads the PMW1 overlay — the demo itself, with compressed pages — switches to protected mode and starts it. No unpacker exists for that format, so the loader was run: Unicorn emulates the real-mode stub, the switch to protected mode (and PMODE/W's own DPMI host), a few DOS calls, until the whole 1.6 MB image sits in memory; it is then cut out of the dump (re/unpack_pmodew.py).
  2. Booting the original. The Watcom start-up code needs a few lies to run (DOS/4G-style signature calls, a heap, VESA answers). With them the original boots in 40 seconds up to the main loop — archive opened, script loaded, 640×480 mode set — and its state is snapshotted. From then on any function of the original can be called with buffers of our choice: that is the ground truth for every port.
  3. The archive. TOUR.98 is a plain sequence of records (sizes, name, compression type, payload). The decoders were found from the loader and re-implemented.
  4. The engine. 56 effects are registered in a table of 20-byte records; each points to a descriptor of three functions (init: parse parameters, run: one frame, free). Each used effect was disassembled, ported, and compared pixel by pixel with the original.

How faithful is the port?

Each effect was compared with the original function running in the emulator on the same input: 2D effects, volumes, cellrd, reebok and echo5 are bit-identical; the 3D pipeline matches to float precision and the rasteriser to within one texel on the silhouettes. Then the whole demo was compared: the original engine was run headlessly from the first frame to the last (4,560 frames at 30 fps) and one frame in fifteen was compared with the port. Mean error: 1.2 levels out of 255 per channel; 94 % of the pixels are within 8 levels; no ten-second stretch averages above 1.9. What is left is mostly the JPEG decoder (the original upsamples chroma without interpolation), fitted colour tables in two 3D scenes, and the explosion of the tentacle in the first half-second. Two details were needed to get there: the C library's rand() state is shared by the texture generator of echo5, the explosion of bomb and the dither noise of cellrd (so each must consume it exactly as the original), and the music clock has to be the player's, not a naive walk of the pattern effects (several channels set the speed on the same row).

About this port

  • Engine: js/engine.js parses the script, schedules commands on the module's (order,row) timeline and runs the events; js/core.js holds the buffer type and the expression compiler; effects live in js/fx/.
  • Music: the original XM module (TOUR3.XM, 2.9 MB) played through libopenmpt (chiptune3).
  • Source and tools: the repository contains the reverse-engineering notes, the emulator harness and the extraction tools (re/, tools/). Sister projects with the same method: 73 million seconds (Pulse, 1998 — the successor of this engine), Zilog, Stars, Saint.
